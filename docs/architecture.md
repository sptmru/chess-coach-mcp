# Architecture and measurement contract

## Boundaries

One modular monolith: HTTP/stdio adapters → typed MCP tools → reusable services → Drizzle/PostgreSQL and a managed UCI process pool. Ingestion, engines and model providers have no access to an arbitrary client-supplied user ID. HTTP authorization establishes a request context; local stdio uses a trusted operator-supplied environment UUID.

Global: public players, immutable imported finished games, normalized moves, compatible objective analysis and grouped critical positions. Personal: associations, classifications, pattern snapshots, coaching profiles/notes/goals/focuses, exercises/sets/attempts and jobs. Shared games have `player_games` rows for each imported player perspective. User-specific rows carry `(identity_id,user_id)` composite foreign keys. UUIDs are identifiers, not authorization. Services check association membership and player color before every position access. Exercise/solution, training set, note mutations, focus mutations and job access independently check the owner. Deleting associations/accounts cascades private state without deleting global games.

Tables and actual relationships: `src/database/schema.ts`; committed incremental SQL: `drizzle/`. The application database role is trusted; this MVP uses repository checks plus relational constraints, not PostgreSQL row-level security. Do not grant clients SQL access.

## Objective evaluation

`Evaluation = {type:'cp', value:number} | {type:'mate', value:number, winning?:boolean}`. Stored engine scores are **White perspective**. `value` for mate preserves Stockfish's signed distance, while `winning` explicitly records whether the perspective side wins, including `mate 0` (JSON cannot preserve the meaning of negative zero). Engine parsing sets this flag; `perspective` transforms it for the player. Positive CP is better for the indicated perspective. Arbitrary-position responses are canonical White; critical positions, comparisons and solutions are player perspective and label that perspective.

For each move, search the before/after FEN at equal configured depth. Numeric CPL is `max(0, before_for_mover - after_for_mover)` only when both scores are CP. Mate transitions return `cpl=null` and retain typed raw scores; neither mate nor infinity is converted to CP. `compare_move` searches the proposed move with UCI `searchmoves` at the original position, using equal root depth. Before/after game CPL has normal finite-depth search noise; it is not a perfectly calibrated accuracy metric. Reports count CP samples separately and exclude mate-score arithmetic.

Win/equal/loss bands: >+150 CP / [-150,+150] / <-150 CP. Mate uses the explicit outcome. Critical threshold is 100 CPL or an important transition; major-mistake threshold is 200. Losing forced mate / allowing forced mate gets severity 1000 **as a grouping priority, not a CP conversion**. Detect win→equal/loss, equal→loss, losing→much worse, failure to punish a preceding opponent error, lost/allowed forced mate, and only-move signals from MultiPV. Positions within four plies of the previous selected position on the same side form a sequence. Highest severity represents the group; all contributing plies are retained. Grouping is an intentionally coarse, replaceable heuristic.

Phase: endgame at <=4 non-pawn/non-king pieces, or <=6 without queens; otherwise opening through ply 20; otherwise middlegame. This is an approximation, not an authoritative phase label.

Clock extraction follows PGN mainline comment order, so repeated FENs do not conflate clocks. chess.js validates moves; the scanner only handles annotations and variation nesting. If mainline clock alignment fails, clocks are omitted. Think time uses the previous same-color clock + increment - current clock for simple seconds/increment controls; negative values, missing clocks and multi-stage controls return null. No clocks are guessed.

## Reproducibility and ingestion

Analysis fingerprints include game ID/content hash, exact Stockfish identity, executable SHA-256, depth, MultiPV, threads, hash allocation, OS/architecture and algorithm version. Hash is cleared before each position. Single-thread mode is the reproducibility default; multithreading can change search results despite identical settings, so exact bitwise reproducibility is not promised there. Compatible concurrent requests share one in-process computation. Run, move analyses and critical positions commit in one transaction; no incomplete run appears completed. Different configurations never overwrite historical runs.

Chess.com requests are serialized, fixed-host, bounded by timeout/response size, and retry network failures/429/5xx with bounded backoff/jitter. Archived months use ETag/Last-Modified. Parsing each game and inserting all moves is atomic. Failed or malformed records do not advance an archive's conditional cache. Standard Rapid chess only is ingested in this initial release; unsupported variants are skipped. UUID or Chess.com game path identifies games; a fallback uses normalized players, date/time, initial FEN and move sequence. Casing is normalized; stable Chess.com `player_id` allows an association to survive username changes. Imported finished games are immutable; upstream corrections require an operator-controlled reimport migration, not a silent update invalidating analysis.

The bundled opening prefixes are original small rules for common openings, supplemented by PGN ECO/Opening/Variation headers. They are not a theory book: `theoryExitPly`, theory deviation and post-theory metrics stay null with an explicit warning. A versioned licensed opening database can be added later.

## Semantic uncertainty

Deterministic features include legal checks/captures, geometric attackers/defenders, undefended attacked pieces, material before/after and check signals. Geometric protection does not account for pinned defenders or tactical exchanges. The deterministic reasoner conservatively labels missed engine-preferred checks/captures, allowed forced mate and measured time correlations; it does not claim a complete fork/pin/king-safety solver. The full requested taxonomy is validated by Zod. Unproven psychological explanations remain `engine_only` or `unclear`.

`PositionReasoner` accepts compact context, not entire games. The real provider adapter supports OpenAI structured Chat Completions, Gemini structured generateContent and Jev's native TypeSafe System One API (`state`, `questions`, `answers`). Jev selects a primary taxonomy label using a Choice question; its confidence and full probability distribution are validated. Explanation/evidence are assembled locally from the selected label and engine facts because Jev does not generate text; secondary labels remain empty. Provider/model selection is restricted to the configured pair or deterministic mock. Labels, raw responses, prompt/schema/taxonomy version, latency, provider usage and nullable cost are separate. Cost stays null unless the adapter knows it; no fabricated pricing. `evaluateLabels` provides an offline manually labeled primary-accuracy/unknown-rate abstraction. Real provider credentials and outputs are not needed by tests.

Patterns choose the newest stored classification per critical position, deduplicate secondary labels and experimental provider outputs, and require >=3 sequences across >=2 games. Trend compares occurrence rates in equal game-count halves, requiring >=3 games per half. Report windows use a single compatible analysis version and disclose excluded games, missing classifications, small samples and truncation. Lack of classified evidence is `insufficient_data`, not “no chess problems”. Pattern snapshots can be recomputed; semantic hypotheses never become objective engine facts.

Coaching context distinguishes computed data from authored notes/repertoire/goals/focuses. Focus baselines are saved at creation, end metrics use compatible analyzed games played after the start timestamp. Rating snapshots are per sampled game. Notes preserve source/time and can be archived. Exercises snapshot solution, engine version and semantic output under an immutable version fingerprint. Public exercise projections never include answer fields. Attempts are append-only with required per-user UUID idempotency keys; result is explicitly self-reported, not automatically graded.

## Operations, limits and next extensions

PostgreSQL-backed job records are executed by bounded in-process workers. One process holds a database advisory lease; interrupted jobs recover on startup and stop retrying after three interruptions. Each user can have five active jobs; global queue cap is 100. Workers check cancellation between archives/games/positions, not halfway through a UCI command. Engine concurrency is separate from job concurrency, bounded by an explicit gate and wait queue. Analysis calls have a process timeout and recover via a fresh UCI process after failure. Shutdown closes transports, jobs, processes and database connections.

HTTP uses the official MCP SDK and OAuth router: Authorization Code, PKCE S256, DCR, fixed callback allowlist, consent-bound HttpOnly SameSite cookie, single-use expiring codes, opaque tokens stored only as SHA-256 hashes, resource binding, one-hour access tokens, rotating 30-day refresh tokens and family revocation on replay. Passwords are scrypt-derived with independent random salts. Auth inputs/PGNs/provider text are untrusted. No Chess.com OAuth or ownership verification is implied.

Limits: 3 identities/user, 1–12 sync months, <=10 analyzed games by default (operator maximum <=50), depth default 12/max16, MultiPV max3, classification batch <=20, exercises <=20, paginated results <=50, report sample <=100, PGN <=500KB/800 plies, MCP input 64KB/output 250KB. Incoming MCP requests are limited per authenticated account; auth endpoints and aggregate ingress also have limits. Forwarded IP headers are intentionally untrusted, so ingress/auth limits are aggregate behind the tunnel. For a larger deployment use a deliberately configured trusted proxy policy and an external identity provider.

Deferred: full licensed opening theory, complete tactical motif recognizer, embeddings/vector similarity, production label evaluation dataset, calibrated puzzle difficulty, automatic training grading, independent worker deployment, HA/multiple replicas, CIMD, external identity provider/password reset/MFA, automatic data retention UI, Prometheus exporter and billing/cost accounting. Existing interfaces and tables provide extension points; none is silently advertised as implemented. Instrumentation counters exist for upstream, engine, jobs, reasoners and MCP; structured logs are stderr-only.
